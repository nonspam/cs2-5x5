# FACEIT_REFERENCE.md — визуальное исследование и история решений

> Документ передачи контекста между чатами. Сохраняет не только итог, но и путь: какие подходы не сработали, что стало переломным моментом, какие материалы изучались и как продолжать. Не выдаёт предположения за измеренные факты.

## 1. Самое важное: как мы нашли правильный путь

Мы хотели сделать профиль игрока и весь CS2 Analytics визуально близкими к FACEIT. Сначала ориентировались в основном на скриншот FACEIT-профиля. По одному скриншоту мы пытались воспроизвести страницу, но результат не складывался: скриншот показывает конечную картинку, но не объясняет внутреннюю систему, которая её создаёт.

Не хватало ответов на вопросы:
- какие реальные DOM-блоки образуют страницу;
- какие классы отвечают за аватар, cover, hero, карточки и статистику;
- какие шрифты используются и где;
- какие градиенты, фоны, размеры, отступы и состояния приходят из CSS;
- как устроены вложенность и responsive правила;
- какие части визуала принадлежат общим компонентам, а какие конкретной странице.

**Переломный момент:** мы перестали пытаться угадать CSS по скриншоту и полезли в исходный HTML и CSS настоящей страницы FACEIT. Как только появился реальный материал, стало возможно опираться на фактические классы, типографику и структуру, а не на визуальные догадки. Именно после этого работа над FACEIT-подобной оболочкой стала предметной и появилась реализация profile shell.

Это главный практический урок проекта: **для точного визуального повторения сначала исследовать источник (HTML + CSS + DOM), а уже потом писать свою разметку и стили.** Скриншот нужен для визуальной сверки, но не должен быть единственным источником правды.

Не возвращаться к циклу «посмотрели скрин — на глаз написали ещё CSS — снова не похоже». Если результат не попадает в референс, сначала проверить структуру, selectors, cascade, fonts и реальные computed styles.

## 4. Какой продукт мы на самом деле строим

Мы не делаем отдельную красивую страницу профиля поверх старого сайта. Пользователь прямо выбрал направление: **единая FACEIT-inspired платформа**, где все разделы ощущаются частями одного продукта.

Общие принципы:
- единая глобальная навигация;
- согласованные фон, типографика, поверхности, границы, интервалы;
- единые tabs, cards, tables, charts, filters и состояния hover/active/focus;
- общий визуальный язык на главной, Players, Profile, Matches, Statistics, Seasons, Track, Records и Settings;
- собственные функции CS2 Analytics оформлять теми же компонентами, даже если прямого аналога в FACEIT нет;
- не копировать FACEIT Play/Queue и другие нерелевантные для нашей платформы элементы;
- не копировать чужие данные OBASRAL, аватар/статистику/историю как данные продукта.

FACEIT — визуальная система и источник UX-паттернов, не спецификация бизнес-логики CS2 Analytics.

## 6. История, которую нельзя потерять

1. **Сначала был подход по скриншоту.** Он не давал точного результата, потому что мы угадывали внутреннюю реализацию по одной картинке.
2. **Затем нашли HTML и CSS реальной страницы FACEIT.** Это стало качественным скачком: можно было исследовать реальные шрифты, selectors, hero/cover/avatar, фоны и карточки.
3. **После исследования источника** мы смогли перейти к реализации цельной профильной оболочки, а не бесконечно подкручивать приблизительные стили.
4. **Дальше выяснилось, что одного профиля недостаточно.** Пользователь хочет единый стиль всего сайта, чтобы не было старого сайта и отдельной новой страницы.
5. **Память проекта переносится в GitHub.** Важно сохранять не только то, что сделали, но и почему выбрали этот путь, какие неудачные подходы уже пробовали и что нельзя повторять.

Следующий чат должен воспринимать эти пункты как накопленный опыт, а не начинать с предложения «давайте попробуем нарисовать профиль по скриншоту».

## 7. Правильный workflow для следующих визуальных задач

### Шаг A — исследование источника
1. Получить исходный screenshot и, если доступно, URL страницы.
2. Получить HTML и все связанные CSS chunks/stylesheets.
3. Зафиксировать viewport, масштаб и состояние страницы (вошедший/гость, активная вкладка).
4. Найти DOM-блоки и сопоставить их с CSS selectors.
5. Изучить fonts, font weights, line-height, colors, gradients, shadows, borders, spacing, radii, breakpoints.
6. Отличить общие FACEIT компоненты от специфичных для профиля.
7. Сохранить результаты в этот документ или отдельные тематические заметки; по возможности сохранить исходники в `docs/reference/faceit/` с указанием источника и даты.

### Шаг B — проектирование своего интерфейса
1. Сопоставить FACEIT-паттерны с реальными сущностями и данными CS2 Analytics.
2. Не копировать DOM бездумно: перенести визуальные принципы и нужные паттерны.
3. Уточнить состояния: loading, empty, error, disabled, hover, active, focus.
4. Определить общий shell и переиспользуемые компоненты.
5. Зафиксировать, какие функции обязаны остаться рабочими.

### Шаг C — реализация
1. Прочитать текущий HTML/JS/CSS и проверить текущие handlers.
2. Найти точку входа и порядок подключения CSS.
3. Использовать scoped root class, если это локальная новая оболочка.
4. Не накапливать конфликтующие правила в конце файла без понимания cascade.
5. Не ломать data bindings, auth, permissions, Supabase и существующие операции.
6. Сначала сделать один эталонный экран, затем переносить систему на остальные разделы.

### Шаг D — визуальная проверка
1. Открыть DEV, а не production.
2. Снять screenshot при том же viewport, что и референс.
3. Сверить размеры и иерархию блоков, шрифты, плотность, отступы и состояния.
4. Проверить узкий экран, горизонтальный overflow, клики, tabs и пустые/error states.
5. Если браузерная проверка недоступна — честно отметить «не проверено», не объявлять pixel-perfect.
6. Сохранить QA evidence и commit SHA.

## 8. Чего не делать
- Не начинать новый визуальный цикл только с попытки угадать CSS по скриншоту, если можно получить исходный HTML/CSS.
- Не выдумывать названия классов, значения CSS, размеры и breakpoints.
- Не утверждать, что перечисленные шрифты используются в конкретном компоненте, пока это не проверено.
- Не считать disabled tabs реализованными.
- Не заменять реальные данные тестовыми данными референсного игрока.
- Не менять production или БД ради визуального эксперимента.
- Не утверждать, что скриншоты совпали, если нет сравнения в браузере.
- Не переписывать всю страницу, пока не изучен текущий DOM и поведение.
