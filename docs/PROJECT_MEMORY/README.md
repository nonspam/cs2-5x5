# CS2 Analytics — Project Memory

> **Единая точка входа для любого нового чата и разработчика.**
>
> Рабочая ветка: `faceit-dev`. Эта память описывает подтверждённое состояние DEV. Production не входит в область текущей работы.

## Если ты — новый ChatGPT: восстанови контекст по последней точке

Пользователь часто переносит работу между чатами и может отправить только эту ссылку. Твоя первая задача — восстановить именно последнее состояние, а не пересказывать старую историю.

1. Прочитай этот README.
2. **Сразу прочитай [SESSION_CHECKPOINT.md](SESSION_CHECKPOINT.md) — это главный файл последней сессии и текущего незавершённого шага.**
3. Прочитай [CURRENT_STATE.md](CURRENT_STATE.md), [NEW_CHAT.md](NEW_CHAT.md), [DEVELOPMENT_LOG.md](DEVELOPMENT_LOG.md) и [QUALITY_HISTORY.md](QUALITY_HISTORY.md).
4. Получи живой HEAD ветки через GitHub API: [faceit-dev branch metadata](https://api.github.com/repos/nonspam/cs2-5x5/branches/faceit-dev). SHA из checkpoint или старого snapshot не считай текущим.
5. Сверь последние коммиты, diff и CI с checkpoint. Если текущая переписка содержит более свежие сообщения/скриншоты владельца, они уточняют или заменяют предварительный handoff.
6. Только после этого кратко сообщи: актуальный HEAD, что уже сделано, где остановились, следующий шаг и что не проверено.

**При конфликте:** живой код и последние сообщения владельца важнее старой записи; SESSION_CHECKPOINT важнее устаревших обобщений; исторический DEVELOPMENT_LOG не является списком текущих задач.

**Если GitHub недоступен:** не делай вид, что прочитал репозиторий, не угадывай HEAD и не меняй код. Назови точный недоступный файл/URL и попроси включить доступ или прислать недостающее. Не проси повторять всю историю.

## Начало работы — читать в этом порядке

1. [SESSION_CHECKPOINT.md](SESSION_CHECKPOINT.md) — последняя точка восстановления, включая IN PROGRESS.
2. [CURRENT_STATE.md](CURRENT_STATE.md) — подтверждённое общее состояние проекта.
3. [NEW_CHAT.md](NEW_CHAT.md) — протокол восстановления и безопасной работы.
4. [DEVELOPMENT_LOG.md](DEVELOPMENT_LOG.md) — смысловая история завершённых и прерванных задач.
5. [QUALITY_HISTORY.md](QUALITY_HISTORY.md) — реальные результаты тестов, QA и deployment.
6. [PROJECT_MASTER.md](../../PROJECT_MASTER.md) — цели, ограничения и принципы продукта.
7. [TECHNICAL_STATE.md](../../TECHNICAL_STATE.md) и [ARCHITECTURE.md](../../ARCHITECTURE.md) — техническое состояние и устройство приложения.
8. [DESIGN_SYSTEM.md](../../DESIGN_SYSTEM.md) и [FACEIT_REFERENCE.md](../../FACEIT_REFERENCE.md) — визуальные правила и референсы.
9. [DECISIONS.md](../../DECISIONS.md) и [ROADMAP.md](../../ROADMAP.md) — принятые решения и будущая очередь.
10. Документы конкретной функции, над которой продолжается работа.

После чтения проверь живую ветку и последние коммиты. Документы не заменяют проверку репозитория.

## Что и когда обновлять

| Документ | Назначение | Обновление |
|---|---|---|
| SESSION_CHECKPOINT.md | **Одна последняя точка восстановления** | После каждого логического шага, а также при прерывании/окончании чата |
| CURRENT_STATE.md | Общая актуальная сводка | После завершённой задачи или изменения текущего фокуса |
| DEVELOPMENT_LOG.md | Смысловая история изменений | После каждого логического пакета; незавершённое помечать IN PROGRESS |
| QUALITY_HISTORY.md | Тесты, CI, QA, deployment evidence | После фактической проверки |
| DECISIONS.md | Долгосрочные решения владельца | Когда владелец явно принимает/меняет решение |
| TECHNICAL_STATE.md / ARCHITECTURE.md / DESIGN_SYSTEM.md / ROADMAP.md | Профильное состояние | Когда соответствующая область действительно меняется |
| CHANGELOG.md | Git metadata и изменённые пути push-коммитов | GitHub Actions |

## Обязательный протокол сохранения после каждого этапа

1. Обновить SESSION_CHECKPOINT.md: что делали, что изменилось, что осталось, следующий конкретный шаг, статус (DONE / IN PROGRESS / BLOCKED), branch и известный commit SHA.
2. Если задача завершена — добавить смысловую запись в DEVELOPMENT_LOG.md с целью, поведением до/после, файлами, реализацией и commit SHA. Если прервана — записать незавершённый статус и точку продолжения.
3. Обновить CURRENT_STATE.md, если изменилось текущее состояние/фокус.
4. Обновить QUALITY_HISTORY.md только фактическими результатами с точным run/commit и ограничениями.
5. Обновить профильные документы/DECISIONS/ROADMAP только при необходимости.
6. Проверить diff, сохранить документы в `faceit-dev`, получить итоговый HEAD и убедиться, что checkpoint не остался позади последнего изменения.
7. В итоговом ответе дать ссылку на SESSION_CHECKPOINT.md и коротко сообщить, что следующий чат должен делать первым.

Не оставлять критически важный статус только в переписке. Не объявлять незавершённую задачу готовой.

## Уровни достоверности

- **Подтверждено кодом** — актуальный исходник проверен.
- **Подтверждено тестом/CI** — есть конкретный результат и commit SHA.
- **Подтверждено browser QA** — действительно проверено в браузере с указанием среды и viewport.
- **Подтверждено deployment** — известны среда и deployed SHA.
- **Решение владельца** — пользователь явно согласовал.
- **Не проверено / предположение / план** — никогда не выдавать за готовую функцию.

Зелёный CI не доказывает browser QA, корректность live data или deployment.

## Автоматизация и её границы

Workflow `.github/workflows/project-memory.yml` автоматически добавляет Git metadata и изменённые пути в корневой CHANGELOG.md. Он не видит частные разговоры ChatGPT и не способен понять смысл задачи. Поэтому помощник обязан обновлять SESSION_CHECKPOINT и смысловые документы вручную при каждом этапе работы.

CHANGELOG — технический журнал push-событий; DEVELOPMENT_LOG — смысловая история; SESSION_CHECKPOINT — только последняя точка продолжения.

## Правила безопасности

- Только `faceit-dev`, если владелец явно не разрешил иное.
- Перед изменениями перепроверять branch HEAD.
- Не менять `main`, production, Supabase, SQL, migrations, RLS, grants или DB без отдельного разрешения.
- Не деплоить и не проводить browser QA без отдельного разрешения.
- Не записывать секреты, токены и приватные данные.
- Не придумывать метрики, тесты, визуальные проверки или deployment status.
