# CS2 Analytics — Project Memory

> **Единая точка входа для любого нового чата и разработчика.**
>
> Рабочая ветка: `faceit-dev`. Эта память описывает только подтверждённое состояние DEV. Production не входит в область текущей работы.

## Если ты — новый ChatGPT: обязательный порядок

Пользователь может отправить только эту ссылку. Не проси его перечислять пути или пересказывать историю, пока сам не выполнил доступные шаги восстановления.

1. Прочитай этот README целиком.
2. Открой [NEW_CHAT.md](NEW_CHAT.md) и следуй его инструкции.
3. Прочитай [CURRENT_STATE.md](CURRENT_STATE.md), [DEVELOPMENT_LOG.md](DEVELOPMENT_LOG.md), [QUALITY_HISTORY.md](QUALITY_HISTORY.md), затем корневые документы проекта по списку ниже.
4. Получи живой HEAD ветки через GitHub API: [faceit-dev branch metadata](https://api.github.com/repos/nonspam/cs2-5x5/branches/faceit-dev). Не используй SHA из этого README или старых snapshot как текущий.
5. Сверь последние коммиты и CI с документацией. Только после этого продолжай работу.

**Если GitHub недоступен:** не делай вид, что прочитал репозиторий, не угадывай HEAD и не меняй код. Скажи, что именно не удалось открыть, и попроси пользователя включить доступ к GitHub или прислать недостающий файл/ссылку. Не проси повторять всю историю проекта.

## Начало работы — читать в этом порядке

1. [CURRENT_STATE.md](CURRENT_STATE.md) — подтверждённое текущее положение и незакрытые задачи.
2. [NEW_CHAT.md](NEW_CHAT.md) — протокол восстановления контекста и безопасной работы.
3. [PROJECT_MASTER.md](../../PROJECT_MASTER.md) — цели, ограничения и принципы продукта.
4. [TECHNICAL_STATE.md](../../TECHNICAL_STATE.md) — техническая история и контрольные точки.
5. [ARCHITECTURE.md](../../ARCHITECTURE.md) — устройство приложения и данные.
6. [DESIGN_SYSTEM.md](../../DESIGN_SYSTEM.md) и [FACEIT_REFERENCE.md](../../FACEIT_REFERENCE.md) — визуальные правила и референсы.
7. [DEVELOPMENT_LOG.md](DEVELOPMENT_LOG.md) — смысловая история законченных задач.
8. [DECISIONS.md](../../DECISIONS.md) — принятые решения и ограничения.
9. [QUALITY_HISTORY.md](QUALITY_HISTORY.md) — фактические результаты тестов и проверок.
10. [ROADMAP.md](../../ROADMAP.md) — очередь и статус будущей работы.
11. Прочитай профильные документы той функции, над которой продолжается работа.

После чтения помощник обязан проверить живую ветку и последние коммиты. Документы не заменяют проверку репозитория.

## Как фиксируется каждая законченная задача

1. DEVELOPMENT_LOG.md: цель, поведение до/после, файлы, реализация, commit SHA.
2. CURRENT_STATE.md: только актуальные подтверждённые факты; устаревшее заменить или пометить историей.
3. Корневой DECISIONS.md: только решения, которые действительно принял владелец.
4. QUALITY_HISTORY.md: точная команда/run, SHA, passed/failed, тип проверки и ограничения.
5. TECHNICAL_STATE.md, ARCHITECTURE.md, DESIGN_SYSTEM.md или ROADMAP.md — если изменилась соответствующая область.
6. Проверить ссылки, согласованность документов и итоговый diff.
7. Зафиксировать изменения в `faceit-dev`, перепроверить итоговый HEAD и сообщить точный SHA.

Не создавать записи ради каждого промежуточного микрошагa. Фиксировать законченные логические пакеты. Прерванную задачу отмечать IN PROGRESS, а не завершённой.

## Уровни достоверности

- **Подтверждено кодом** — проверен актуальный исходник.
- **Подтверждено тестом/CI** — есть конкретный результат и commit SHA.
- **Подтверждено browser QA** — действительно проверено в браузере с указанием среды и viewport.
- **Подтверждено deployment** — известны среда и deployed SHA.
- **Решение владельца** — пользователь явно согласовал.
- **Не проверено / предположение / план** — никогда не выдавать за готовую функцию.

Зелёный CI не доказывает browser QA, правильность live data или deployment.

## Автоматизация и её границы

Workflow `.github/workflows/project-memory.yml` автоматически дополняет корневой CHANGELOG.md Git metadata и изменёнными путями. Он не читает частные разговоры ChatGPT и не объясняет смысл изменений. Смысловую запись обязан создать помощник.

CHANGELOG — технический журнал push-событий, DEVELOPMENT_LOG — смысловой журнал завершённых задач. Не подменять одно другим.

## Правила безопасности

- Только `faceit-dev`, если владелец явно не разрешил иное.
- Перед изменением заново проверить branch HEAD; перед следующим набором изменений проверить снова.
- Не менять `main`, production Supabase или production deployment.
- Не выполнять SQL, migrations, RLS, grants или DB writes без отдельного разрешения.
- Не деплоить и не проводить browser QA без отдельного разрешения.
- Не записывать секреты, токены и приватные данные аккаунтов.
- Не придумывать метрики, тестовые результаты, визуальные проверки или состояние функций.
