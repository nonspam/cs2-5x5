# New Chat — CS2 Analytics

## Старт: пользователь может прислать только одну ссылку

Единая точка входа:

`https://github.com/nonspam/cs2-5x5/blob/faceit-dev/docs/PROJECT_MEMORY/README.md`

Пользователь переносит работу между чатами. Не проси его пересказывать историю. Сам восстанови последнюю точку по протоколу.

## Обязательный порядок восстановления

1. Прочитай `docs/PROJECT_MEMORY/README.md`.
2. **Немедленно прочитай `docs/PROJECT_MEMORY/SESSION_CHECKPOINT.md`. Это главная запись о последнем обновлении, текущей задаче и следующем шаге.**
3. Прочитай CURRENT_STATE.md, этот NEW_CHAT.md, DEVELOPMENT_LOG.md и QUALITY_HISTORY.md.
4. Проверь живой HEAD через `https://api.github.com/repos/nonspam/cs2-5x5/branches/faceit-dev`.
5. Получи последние коммиты ветки faceit-dev. Изучи все коммиты новее SHA в checkpoint, включая diff и изменённые файлы.
6. Сверь последнюю запись checkpoint с реальными исходниками и последними сообщениями владельца в текущем чате.
7. Проверь CI/job logs, если качество важно для следующего шага. Не считай зелёный CI доказательством browser QA или deployment.
8. Кратко сообщи владельцу: текущий HEAD, что последнее было сделано, где остановились, следующий шаг, что не проверено.
9. Продолжай именно незавершённую задачу, не возвращайся к старым пунктам без подтверждения.

### Приоритет источников при расхождении

1. Живой код и HEAD ветки.
2. Самые свежие сообщения/скриншоты владельца в текущем чате.
3. SESSION_CHECKPOINT.md — последняя записанная точка.
4. CURRENT_STATE.md и актуальные профильные документы.
5. DEVELOPMENT_LOG.md — история, не текущий todo.
6. Старые чаты и старые handoff — только справка.

Если новый пользовательский фидбек свежее checkpoint, обнови checkpoint перед завершением текущего логического этапа. Не игнорируй новое ради старой записи.

### Если GitHub/файл недоступен

Не утверждай, что прочитал недоступный файл, не угадывай HEAD и не меняй репозиторий, пока не подтверждены ветка и актуальное состояние. Назови точный URL/файл, который не открылся. Не заставляй пользователя повторять всю историю.

## Протокол записи каждой сессии и каждого логического этапа

До завершения чата, а также после каждого законченного пакета изменений:

1. Обнови SESSION_CHECKPOINT.md. Он должен содержать:
   - дату и branch;
   - SHA до/после (если известен);
   - текущую задачу и статус DONE / IN PROGRESS / BLOCKED;
   - что пользователь попросил и что одобрил;
   - что фактически изменено (файлы и поведение);
   - какие тесты/проверки реально выполнены и их результат;
   - что НЕ проверено (browser QA, screenshots, deployment, DB — если применимо);
   - точный следующий шаг;
   - любые новые пользовательские скриншоты/уточнения, влияющие на задачу.
2. Обнови DEVELOPMENT_LOG.md смысловой записью. Незавершённое не маскируй под завершённое.
3. Обнови CURRENT_STATE.md, если поменялся фокус или состояние проекта.
4. Обнови QUALITY_HISTORY.md только по реальным evidence.
5. Обнови профильные документы и DECISIONS.md, если действительно изменились архитектура, правила или принятое владельцем решение.
6. Сохрани всё в faceit-dev, проверь итоговый HEAD и убедись, что checkpoint отражает самый последний этап.
7. В ответе дай ссылку на SESSION_CHECKPOINT.md.

**Не заканчивай работу с важным новым решением/статусом, оставленным только в сообщениях чата.** Если чат обрывается внезапно, последний сохранённый checkpoint должен позволить восстановить как минимум предыдущий завершённый этап; после каждого логического этапа обновляй его, не жди конца чата.

## Непереговорные ограничения проекта

- Рабочая ветка только `faceit-dev`.
- Перед каждым набором изменений заново проверить HEAD.
- Не трогать `main` и production.
- Никаких DB writes, SQL, migrations, RLS, grants, schema или Edge Function изменений без отдельного разрешения.
- Никакого deployment или browser QA без отдельного разрешения.
- Не выдумывать игровые данные, метрики, результаты тестов, визуальную проверку или статус deployment.
- Сохранять существующее рабочее поведение и добавлять regression coverage для кодовых изменений.

## Стиль работы

- Русский язык, просто и прямо.
- Не заставлять владельца повторять известный контекст.
- Для визуальных задач ориентироваться на самые свежие скриншоты/референсы.
- Чётко разделять исходники, CI, browser QA и deployment.
