# CS2 5x5 — план следующих объёмных этапов

Дата фиксации: 22.10.2026  
Репозиторий: `nonspam/cs2-5x5`, ветка `main`.

Это рабочий план следующей серии крупных пакетов работ. Этапы объединяются в большие логические пакеты, но каждый пакет должен иметь проверяемые критерии готовности. Не смешивать безопасный кодовый рефакторинг с рискованными изменениями живых данных.

## Цель
Сделать сайт надёжным в повседневном использовании: статистика соответствует сохранённым данным, создание и редактирование матчей не теряют игроков, сохранение предсказуемо, расчёты проверяемы, интерфейс остаётся простым и привычным. Затем развивать аналитику без ухудшения текущего сайта.

## Пакет 1 — P0: целостность данных и достоверность статистики
**Задачи**
- Провести актуальный read-only аудит состояния Supabase и сверить его с тем, что показывает сайт: серии, карты, архивные записи, порядок серий, последние игры игрока, счётчики и агрегаты.
- Найти причину любых расхождений между списком серий, последними сериями игрока и общими счётчиками. Проверить идентификаторы, сортировку, фильтры активности/архива, источники данных и кэш; не ограничиваться косметической правкой сортировки.
- Разобрать строки статистики без `player_id` (последний известный снимок: 95 строк) и составить отчёт с исходными именами и привязками к сериям/картам. Не сливать игроков и не создавать профили автоматически.
- Проверить, что расчёты исключают архив корректно и восстанавливают запись после restore.
- Сверить неполные лобби, гостевые имена и агрегированные серии BO3: не создавать отсутствующие K/D/A и не превращать неизвестные значения в нули.
- До любой потенциальной массовой коррекции сделать резервную копию, diff и план отката; все изменения живых данных — отдельной согласованной и проверяемой операцией.

**Критерии завершения**
- Счётчики и списки согласованы с каноническим состоянием.
- Для последних серий игрока можно объяснить происхождение каждой записи и порядок сортировки.
- Неопределённые личности выделены явно, а не угадываются.
- Нет неподтверждённых массовых изменений в продакшене.

## Пакет 2 — P0: регрессионная защита ключевых сценариев
**Задачи**
- Укрепить `npm run check` и тесты на реальные контракты активного `index.html`: подключаемые скрипты, версии/cache-busting и отсутствие ссылок на устаревшие entrypoints.
- Добавить автоматизированные сценарии для создания неполного матча, BO1/BO3/BO5, порядка карт, состава двух команд, сортировки игроков по K/D, расчёта K/D/A и отображения последних серий.
- Проверить путь сохранения: валидация → commit с ожидаемой версией → конфликт версии/ошибка сети → понятное сообщение → reload → повторное открытие.
- Проверить административные действия в безопасной тестовой среде: вход, создание, редактирование, архив, восстановление и окончательное удаление с подтверждением.
- Отличать в отчётах тесты кода, успешный CI, деплой Pages и реальную проверку сайта в браузере.

**Критерии завершения**
- Основные регрессии ловятся автоматически.
- Тесты не меняют production-данные.
- Для каждого релиза понятен набор реально пройденных проверок.

## Пакет 3 — P0/P1: корректность редактора матчей и составов
**Задачи**
- Аудировать создание и редактирование матчей: сохраняются ровно введённые поля, неполные составы разрешены, нет неявного требования ровно 10 игроков.
- Проверить добавление игроков в серии и отдельные карты, принадлежность к командам, отсутствие дублей и потерянных строк после перезагрузки.
- Проверить корректный пересчёт K/D/A после редактирования и не затрагивать другие матчи.
- Для строк без статистики отличать «нет данных» от настоящего значения 0; не показывать ложные `-/-/-` как будто это вычисленный результат.
- Проверить порядок игроков внутри команд по K/D по убыванию; определить и протестировать стабильное поведение для одинакового K/D и неизвестных значений.
- Повторно проверить пользовательские случаи: матчи 17, 18, 19, 25–39, 42–43, 63–64 — только на чтение вначале; уже подтверждённые данные не переписывать без воспроизводимой ошибки.

**Критерии завершения**
- Созданный/отредактированный матч после reload совпадает с введёнными данными.
- Командные списки упорядочены по K/D и не теряют участников.
- Не возникает побочных изменений в несвязанных матчах.

## Пакет 4 — P1: расчётные функции и прозрачность Player Index
**Задачи**
- Сверить формулу Player Index с `docs/DATA_MODEL.md` и реальным кодом.
- Добавить golden-тесты для формулы и пограничных ситуаций: 0 смертей, пустая выборка, агрегированная BO3, мало сыгранных карт, архив, неполные данные.
- Отображать/документировать достаточность выборки и покрытие подробной статистикой так, чтобы индекс не выглядел точнее, чем позволяют данные.
- Не менять веса или смысл показателей только ради улучшения рейтинга; любое изменение — отдельное решение с before/after на известных наборах данных.

**Критерии завершения**
- Для ключевых примеров расчёт воспроизводим тестами.
- Пользователь может понять, что означает индекс и насколько он надёжен при его объёме данных.

## Пакет 5 — P1: поддерживаемость кода без смены дизайна
**Задачи**
- Составить карту активных файлов, устаревших копий, тестов и релизных действий.
- Постепенно вынести чистые функции расчётов, сортировки и форматирования из большого `app_v57.js` в небольшие модули, если сборка/Pages это поддерживают.
- Каждый шаг рефакторинга должен сохранять UI и иметь тесты на прежнее поведение.
- Проверить обработку ошибок Supabase, состояния загрузки/сохранения, realtime и конфликтов версии.
- Не удалять резервные файлы, пока не проверены ссылки, необходимость для QA и путь отката.

**Критерии завершения**
- Меньше логики, которую можно случайно сломать одной правкой.
- Нет необоснованного изменения визуального интерфейса.
- Деплой и загрузка всех активных файлов проверяются автоматически.

## Пакет 6 — P1/P2: удобство и согласованность интерфейса
**Задачи**
- Проверить dropdown/селекторы игроков, карт, создания матча и фильтров: быстрое открытие вниз, удобный размер списка, отсутствие ненужной внутренней прокрутки.
- Исправить взаимодействие фильтров карты и игрока так, чтобы показывались только совпадающие игры.
- Проверить отсутствие дублирования игрока/статистики в таблицах.
- Убедиться, что в «Последних сериях» исход серии (WIN/LOSS/DRAW) и цвет K/D/счёта отображаются по разным правилам: результат серии не должен перекрашивать положительный личный K/D в красный.
- Не менять дизайн глобально; делать только точечные, проверяемые улучшения.

**Критерии завершения**
- Фильтры работают совместно, списки удобны, дубли отсутствуют.
- Цвета результата серии и индивидуальной статистики логически независимы.

## Пакет 7 — P2: полезная аналитика матчей и игроков
Начинать только после закрытия P0 и подтверждения целостности данных.

**Задачи**
- Детали обычного матча: Top 10 по K/D, затем две команды с K/D/A и сортировкой по K/D.
- Сравнение игроков с ясным объяснением, кто в чём сильнее, без декоративного нагромождения метрик.
- Форма и стабильность с размером выборки и понятным объяснением, почему оценка могла измениться.
- Аналитика карт по фактическим данным с явным обозначением недостаточной выборки.
- Использовать существующий стиль сайта как ориентир; не превращать его в перегруженный профессиональный портал.

**Критерии завершения**
- Каждая новая метрика имеет понятный смысл, проверенные расчёты и не вводит в заблуждение при малой выборке.

## Порядок выполнения и правила работы
1. Сначала Пакеты 1–3 (P0): данные, регрессионная защита, редактор и составы. Допустимо объединять их в крупные пакеты реализации, но аудит и тестирование должны предшествовать рискованным изменениям.
2. Затем Пакеты 4–6 (P1): формулы, поддерживаемость и точечный UX.
3. После подтверждения стабильности — Пакет 7 (P2): аналитика.
4. В начале каждой крупной работы повторно читать актуальный код `main` и проверять состояние Supabase read-only. При расхождении документа с кодом/данными приоритет у проверяемого актуального состояния.
5. Перед правками сохранять контрольную точку; после правок запускать тесты, проверять CI и Pages deployment, а живой браузер обозначать как непроверенный, если его фактически не проверяли.
6. Не выдавать предположения за факты, не говорить «готово», пока критерии завершения не пройдены.
7. Не переписывать сайт с нуля, не менять подтверждённые данные ради интерфейса, не выполнять разрушительные операции в production без резервной копии и явного обоснования.

## Отчёт о ходе
Статус всех пакетов на момент создания документа: **запланированы; не считать завершёнными по факту записи этого плана**. При закрытии каждого пакета обновлять этот документ отдельным коммитом: что изменено, какие тесты пройдены, какие проверки не выполнены, остаточные риски.
